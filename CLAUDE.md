## Architecture diagram

`docs/architecture.dot` is the source of the architecture diagram. When a change adds, removes or renames a project, component, service or entity, or changes the dependencies between them, update the dot file in the same change.

`dotnet build` renders `docs/architecture.svg` and `docs/architecture.png` from it if the Graphviz `dot` command exists, and skips this step otherwise. Commit the rendered files together with the dot file and never edit them by hand.

## Code conventions (all projects, tests included)

- No primary constructors on classes. Use an explicit constructor and `private readonly _field`s. Positional records are fine.
- Keep members as private as possible. Tests go through the public API, not internals.
- Use the classic switch statement (`switch (value) { case X: ... }`), no switch expressions. Cases assign a variable and end with `break`, and the method returns the variable after the switch.
- Every test method gets a `///` summary saying what it tests: the scenario and the expected result. Test classes get a summary of what the whole class covers.

## Database

- A `Code` column in any table must be unique for each row. `AppDbContext` adds the unique index to every entity with a `Code` property, so do not remove this or rename the property to avoid it.
- Codes are generated by the database from the id, with a prefix for each type of record and six digits: `KLI_000001` for clients, `KAT_000001` for categories, `PROD_000001` for products. Never set them in code. The prefixes are in `RecordCode`, and the code search uses them to recognize the record type. A new type with a `Code` gets a new prefix and the same generated column.
- Test data is in `src/StockManager.Server/Data/seed.sql`. It sets ids, which give the codes, and other rows refer to records by code. Keep the file in sync with the model, because table and column names are written there by hand.

## Comments

Readers are senior .NET developers: comment intent, never explain language or framework features.

- Every block of code (statements separated by a blank line) gets a comment above it saying what it does.
- Complex logic (locking, retries, cancellation, concurrency) may be commented line by line.
- As short and high level as possible, one line is the norm.
- Single sentence: lowercase, no trailing period. Multiple sentences and `///` docs: normal sentence style.
- Classes, interfaces and larger units (services, handlers, DI setup) get a `///` summary in normal sentence style. It may be longer: describe at a high level everything the unit is responsible for and how it fits into the service.
- Every method and local function gets a `///` summary, including private ones and overrides. A short one-sentence summary is enough. Use `<inheritdoc />` only when the inherited doc already says everything.
- Keep "why" comments next to the "what" comments.
- Plain, simple English that non-native speakers read easily. No idioms or figurative words ("stand-in", "goes out", "fail fast"), say it literally ("instead of", "is sent", "throw"). Domain terms used in the code (seed, stock, lookup) are fine.
